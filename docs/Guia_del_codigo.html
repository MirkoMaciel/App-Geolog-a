2. Qué hace la app y con qué está hecha

Funcionalidad

  • Recorrido: una salida de campo. Tiene nombre, tipo de salida (por ahora "Suelos"), proyecto, descripción y estado (en curso / finalizado).
  • Parada: un punto del recorrido. Guarda la hora, la posición (GPS, a mano o tocando el mapa) y los datos generales del sitio (calicata, geomorfología, vegetación…).
  • Item: una observación dentro de la parada: título, descripción, fotos y, opcionalmente, los datos de la planilla de suelos (lo que en papel es una columna de la tabla).
  • Exportación: un PDF de la parada o del recorrido completo, con el formato de la planilla en papel y una ficha por item con sus fotos. Quedan guardados en "Mis exportaciones".

El flujo de datos es en una sola dirección

Este es el patrón más importante para entender la app (se llama flujo unidireccional):

El usuario toca o escribe→ La pantalla llama a una función del ViewModel→ El repositorio actualiza la lista en memoria→ El StateFlow emite la lista nueva→ Compose redibuja las pantallas que la usan

En paralelo, el repositorio escribe el JSON en segundo plano. Las pantallas nunca modifican los datos directamente: siempre piden el cambio y esperan a que les llegue el estado nuevo.

// Navegacion.kt — la interfaz "escucha" la lista de recorridos
val recorridos by viewModel.recorridos.collectAsStateWithLifecycle()

// ListaRecorridosScreen — al crear, se llama al ViewModel (no se toca la lista)
onCrearRecorrido = { nombre, tipo, proyecto, descripcion ->
    val id = viewModel.crearRecorrido(nombre, tipo, proyecto, descripcion)
    navController.navigate(RutaRecorrido(id))
}

¿Por qué un ViewModel?

Cuando girás el teléfono, Android destruye y vuelve a crear la pantalla (la Activity). Todo lo que estaba en variables comunes se pierde. El ViewModel sobrevive a ese proceso, por eso los datos viven ahí y no en las pantallas.

5. Conceptos de Compose que vas a ver en el código

Funciones @Composable

Una pantalla o un pedazo de pantalla es una función marcada con @Composable. No devuelve nada: describe lo que se ve. Compose la vuelve a ejecutar (recomposición) cada vez que cambia un dato que lee.

// ui/inicio/InicioScreen.kt
@Composable
private fun Contador(titulo: String, valor: Int, modifier: Modifier = Modifier) {
    Card(modifier = modifier) {
        Column(horizontalAlignment = Alignment.CenterHorizontally) {
            Text(valor.toString(), style = MaterialTheme.typography.headlineMedium)
            Text(titulo, style = MaterialTheme.typography.labelMedium)
        }
    }
}

Estado: remember, mutableStateOf y rememberSaveable

HerramientaQué haceEjemplo en la app
mutableStateOf(x)Una variable que, al cambiar, provoca que se redibuje lo que la usa.El texto de un campo, si un diálogo está abierto.
remember { }Conserva el valor entre recomposiciones (si no, se reiniciaría cada vez).var parada by remember { mutableStateOf(paradaGuardada) }
rememberSaveable { }Igual, pero además sobrevive a girar la pantalla.La pestaña elegida, si el diálogo "Nuevo recorrido" está abierto.

Modifier

Es la forma de decirle a un componente su tamaño, márgenes, fondo o qué hacer al tocarlo. Se encadena y el orden importa:

Modifier.fillMaxWidth().padding(16.dp).clickable { onAbrir(item.id) }

Scaffold

La estructura de cada pantalla: barra superior (topBar), botón flotante (floatingActionButton), menú inferior (bottomBar) y mensajes (snackbarHost). El contenido recibe un innerPadding para no quedar tapado por las barras.

Efectos: LaunchedEffect y DisposableEffect

Sirven para ejecutar código "por fuera" del dibujo. La app los usa para el autoguardado:

// ui/recorridos/EditarItemScreen.kt
LaunchedEffect(item) {      // se reinicia cada vez que cambia "item"
    delay(500)              // si en medio segundo hay otro cambio, se cancela y empieza de nuevo
    onGuardar(item)         // → se guarda 0,5 s después de dejar de escribir
}
DisposableEffect(Unit) { onDispose { onGuardar(actual) } }  // y al salir de la pantalla

Abrir otras apps y pedir permisos: rememberLauncherForActivityResult

Para abrir la cámara, la galería, el selector de "Guardar como" o pedir permisos, Android usa contratos. Se registra un "lanzador" con lo que hay que hacer cuando vuelve el resultado, y después se llama a launch():

// ui/recorridos/EditarItemScreen.kt
val lanzadorCamara = rememberLauncherForActivityResult(ActivityResultContracts.TakePicture()) { ok ->
    if (ok) importarFotos { listOf(almacenFotos.importarArchivo(temporal)) }
}
lanzadorCamara.launch(uri)   // abre la cámara; la foto se escribe en "uri"

6. Los datos: modelos y repositorio

Modelos.kt

data/recorrido/Modelos.kt

Define la forma de los datos con data classes (clases que solo guardan datos; Kotlin les genera copy(), equals(), etc.). Todas tienen @Serializable para poder convertirse a JSON.

Recorrido
id, nombre, tipoSalida, proyecto, finalizado…contiene → Parada (lista)
fecha, latitud, longitud, altitud, observacionescontiene → DatosSitio
calicata, geomorfología, relieve… ItemParada (lista)
título, descripción, fotos + campos de suelo

Detalles a observar

  • Todo es inmutable (val). Para cambiar algo se crea una copia: item.copy(titulo = "Nuevo"). Esto hace que Compose detecte los cambios con seguridad.
  • Valores por defecto en casi todos los campos: si mañana se agrega un campo nuevo, los JSON viejos se siguen pudiendo leer.
  • Migración: en la primera versión los items se llamaban "horizontes". @JsonNames permite leer ambos nombres: 
    @JsonNames("horizontes") val items: List<ItemParada> = emptyList(),
  • tieneDatosSuelo() decide si un item va como columna en la tabla del PDF. El truco: borra los campos que no son de suelo y compara contra un item vacío. 
    fun ItemParada.tieneDatosSuelo(): Boolean =
    copy(id = 0, titulo = "", descripcion = "", fotos = emptyList(), fecha = 0) != ItemParada(id = 0)
  • Las fotos se guardan como nombres de archivo (List<String>), no como imágenes: las imágenes están en una carpeta aparte.

OpcionesSuelo.kt

data/recorrido/OpcionesSuelo.kt

Las opciones fijas de la planilla. Cada Opcion tiene un código (lo que se imprime: "MA") y una descripción (lo que se lee en la app: "Muy abrupto"). En los datos se guarda solo el código.

GrupoOpciones agrupa las opciones en líneas: casi todas van en una línea, pero adhesividad y plasticidad ocupan dos, igual que en la planilla en papel. El PDF usa esas líneas para dibujarlas.

También tiene listas de sugerencias para campos de texto libre (texturas, tipos de estructura…). Si la cátedra quiere cambiar opciones o sugerencias, este es el único archivo que hay que tocar.

RecorridoRepository.kt

data/recorrido/RecorridoRepository.kt

Es el único lugar que modifica los datos y el único que lee y escribe el archivo recorridos.json.

Cómo funciona

  1. Al crearse, lee el JSON y lo carga en un MutableStateFlow (una "caja" observable con la lista de recorridos).
  2. Expone esa caja como recorridos: StateFlow de solo lectura. Las pantallas la observan.
  3. Todas las modificaciones pasan por modificar(): aplica el cambio en memoria (la pantalla se actualiza al instante) y lanza la escritura del archivo en segundo plano.
private fun modificar(cambio: (List<Recorrido>) -> List<Recorrido>) {
    _recorridos.update(cambio)          // 1) memoria → la interfaz se redibuja
    scope.launch { escribirArchivo() }  // 2) disco, en otro hilo
}

Las funciones públicas (crearParada, guardarItem, eliminarItem…) se construyen encima de dos ayudantes: modificarRecorrido(id) y modificarParada(recorridoId, paradaId), que buscan el elemento y reemplazan solo ese.

Detalles de robustez (pensados para el trabajo de campo)

  • Escritura atómica: se escribe en recorridos.json.tmp y después se renombra. Si el teléfono se apaga a mitad de camino, el archivo original queda sano.
  • Archivo dañado: si el JSON no se puede leer, se guarda una copia .danado antes de empezar de cero, para poder recuperar los datos.
  • Ids únicos: nuevoId() usa la hora en milisegundos, pero nunca repite aunque se creen dos cosas en el mismo milisegundo.
  • guardarParada() no pisa los items: conserva los items que ya estaban guardados. Así, si la pantalla de la parada y la del item guardan casi al mismo tiempo, no se pierden cambios.
  • El Mutex evita que dos escrituras del archivo se mezclen.

RecorridosViewModel.kt

ui/recorridos/RecorridosViewModel.kt

Es casi un "pasamanos" hacia el repositorio, más dos responsabilidades propias:

  • Cuando se elimina un item, parada o recorrido, borra también sus fotos del almacenamiento.
  • Al arrancar, borra las fotos sueltas que no pertenezcan a ningún item (eliminarNoUsadas), por ejemplo si se quitó una foto de un item.

Es un AndroidViewModel porque necesita el Application para saber dónde está la carpeta de archivos de la app (filesDir). Hay uno solo para toda la app; se crea en Navegacion.kt con viewModel() y se pasa a las pantallas.

DetalleRecorridoScreen.kt

ui/recorridos/DetalleRecorridoScreen.kt

Mapa arriba, lista de paradas abajo. Las tres formas de crear una parada terminan en la misma función, crearYAbrir():

  • GPS: rememberSolicitudUbicacion pide permiso, busca la posición y devuelve un ResultadoUbicacion (Exito, SinPermiso o NoDisponible).
  • A mano: crea la parada sin coordenadas y abre el editor.
  • Mantener presionado el mapa: MapaRecorrido avisa con onMantenerPresionado(lat, lon) y se pide confirmación.

El menú ⋮ permite finalizar o reabrir el recorrido y eliminarlo; el ícono de compartir exporta el recorrido completo.

EditarParadaScreen.kt

ui/recorridos/EditarParadaScreen.kt
  • Estado local + autoguardado: la pantalla edita una copia local (var parada by remember) y la guarda medio segundo después de cada cambio y al salir. Trabajar con una copia local evita problemas con el cursor al escribir rápido.
  • Los items no se editan acá: la lista de items se lee de paradaGuardada (lo que está en el repositorio), y agregar o eliminar items se pide directamente al ViewModel.
  • Coordenadas como texto: latitud, longitud y altitud se editan como String y se convierten a número con parsearCoordenada(), que acepta coma o punto y valida el rango (±90 / ±180).
  • ResumenParada muestra siempre la hora y la posición; las pestañas son "Items" y "Ubicación y sitio".

EditarItemScreen.kt

ui/recorridos/EditarItemScreen.kt
  • Mismo patrón de estado local + autoguardado que la parada.
  • Cámara: AlmacenFotos.nuevoArchivoCamara() crea un archivo temporal y su Uri; la cámara escribe ahí. La ruta se guarda con rememberSaveable porque Android puede cerrar la app mientras la cámara está abierta.
  • Galería: PickMultipleVisualMedia devuelve hasta 10 Uri; cada una se importa con importarUri().
  • importarFotos() procesa las fotos en otro hilo (Dispatchers.IO) y muestra un indicador de carga mientras tanto (procesando).
  • CamposSuelo contiene todos los campos de la planilla; se muestra u oculta con mostrarSuelo, que arranca abierto si el item ya tiene datos de suelo.

ExportacionesScreen.kt y componentes

ui/exportaciones/ · ui/componentes/

ExportacionesScreen lista los PDFs de la carpeta de exportaciones (los vuelve a leer cada vez que se entra) y permite verlos, compartirlos o borrarlos.

CamposFormulario.kt tiene los bloques que se repiten en los formularios: CampoTexto, SelectorOpciones (chips; tocar la opción elegida la desmarca), CampoConSugerencias, TituloSeccion y funciones para formatear fechas y coordenadas. Fotos.kt tiene MiniaturaFoto y VisorFoto; ambas cargan la imagen achicada en segundo plano con produceState.

8. Mapa, GPS y fotos

MapaRecorrido.kt

ui/recorridos/MapaRecorrido.kt
  • El MapView de osmdroid se crea una sola vez con remember y se muestra con AndroidView. El bloque update se ejecuta en cada recomposición: borra y vuelve a dibujar los marcadores y la línea del recorrido.
  • Ciclo de vida: el mapa necesita enterarse de cuándo la pantalla se pausa o se reanuda. Se hace con un LifecycleEventObserver dentro de un DisposableEffect.
  • Error 403 de OpenStreetMap: OSM exige que cada app se identifique. osmdroid reemplaza la identificación por el nombre del paquete (com.example…), que OSM bloquea. Por eso se define MOSAICOS_OSM a mano, sin esa opción, y la app se identifica como "AppGeologia/1.0".
  • iconoNumerado() dibuja con Canvas el círculo marrón con el número de la parada.
  • clipToBounds() evita que el mapa se dibuje por fuera de su recuadro.

Ubicacion.kt

ubicacion/Ubicacion.kt
  • obtenerPosicionActual() es una función suspend: espera la posición sin bloquear la pantalla. Usa el GPS si está activado y, si no, la red.
  • suspendCancellableCoroutine convierte la respuesta "con callback" de Android en algo que se puede esperar con una corrutina.
  • Si en 30 segundos no llega una posición nueva (withTimeoutOrNull), usa la última posición conocida.
  • rememberSolicitudUbicacion() empaqueta todo para las pantallas: pide permiso si hace falta, busca y avisa el resultado. Además expone buscando para mostrar "Buscando señal GPS…".

AlmacenFotos.kt

archivos/AlmacenFotos.kt

Cada foto importada pasa por guardar():

  1. Medir sin cargar: inJustDecodeBounds = true lee solo el tamaño (una foto de 50 MP no entraría en memoria).
  2. Cargar reducida: inSampleSize carga la imagen ya achicada a la mitad, a un cuarto, etc.
  3. Escalar y enderezar: con una Matrix se lleva a 2048 px como máximo y se rota según el dato EXIF de orientación (las cámaras guardan muchas fotos "acostadas" con una marca que indica cómo rotarlas).
  4. Guardar como JPEG calidad 85 con un nombre único (UUID).

cargarReducida() se usa para miniaturas (320 px), el visor (2048 px) y el PDF (1200 px).

AlmacenExportaciones.kt

archivos/AlmacenExportaciones.kt

Maneja la carpeta exportaciones/. nuevoArchivo() agrega fecha y hora al nombre para no pisar exportaciones anteriores. verPdf() y compartirPdf() usan un Intent con una Uri del FileProvider: otras apps no pueden leer los archivos privados de la app directamente, así que se les da un permiso temporal (FLAG_GRANT_READ_URI_PERMISSION).

9. Generación del PDF

PlanillaPdf.kt

pdf/PlanillaPdf.kt

Android trae PdfDocument: cada página es un Canvas (un lienzo) donde se dibujan líneas, rectángulos y texto en coordenadas. La unidad es el punto (1/72 de pulgada); una hoja A4 mide 595 × 842 puntos. El origen (0, 0) está arriba a la izquierda y la y crece hacia abajo.

Recorrido del código

FunciónQué dibuja
generarParada() / generarRecorrido()Puntos de entrada. El recorrido agrega una carátula y luego cada parada.
Documento (clase interna)Abre y cierra páginas, lleva el número de página y agrega el pie.
dibujarParada()Divide los items con datos de suelo en grupos de 4 (una página de tabla por grupo), agrega observaciones y fichas.
dibujarEncabezado()El recuadro de datos del sitio en tres columnas (Calicata, Coordenadas, Geomorfología…).
dibujarTablaHorizontes()La tabla: recorre la lista filas y dibuja etiqueta + 4 celdas por fila; después la columna vertical de grupos y la subcolumna "Forma".
dibujarOpciones()Imprime "MA – A – C – G – D" y encierra la elegida en un óvalo rojo, en negrita.
dibujarFichasItems()Una ficha por item: encabezado, descripción y fotos en dos columnas; salta de página cuando no entra.
dibujarFoto()Escala la foto para que entre en su celda sin deformarse.
textoAjustado()Escribe texto con saltos de línea (StaticLayout) y achica la letra hasta que entre en la celda.
textoVertical()Los títulos rotados 90° (Límite, Consistencia…); parte en dos líneas si no entran.

La tabla está definida como datos

En vez de escribir 29 filas a mano, hay una lista filas. Cada Fila dice a qué grupo pertenece, su etiqueta, qué campo del item mostrar y, si corresponde, sus opciones:

Fila("Límite", "Definición", { it.limiteDefinicion }, OpcionesSuelo.limiteDefinicion, altoFila),
Fila("Color", "Seco", { it.colorSeco }, alto = altoFila),

Las filas con el mismo grupo consecutivo forman la columna vertical. Para agregar una fila al PDF, alcanza con agregar un elemento a esta lista.

Cómo se verificó: la prueba PlanillaPdfTest genera un PDF con datos de ejemplo, cuenta las páginas y guarda cada página como imagen PNG para revisarla a ojo (ver capítulo 12).

10. Flujos completos paso a paso

A. Crear un recorrido

Inicio: "Hacer un nuevo recorrido"→ DialogoNuevoRecorrido→ viewModel.crearRecorrido()→ repo.crearRecorrido() agrega a la lista y escribe el JSON→ navigate(RutaRecorrido(id))

"Nueva parada" → "Usar mi ubicación"→ ubicacion.solicitar()→ ¿Hay permiso? Si no, se pide→ obtenerPosicionActual()→ ResultadoUbicacion.Exito→ crearYAbrir(lat, lon, alt, precisión)→ Editor de la parada

C. Agregar un item con una foto

"Agregar item u observación"→ viewModel.agregarItem() devuelve el id→ navigate(RutaItem(…))→ "Tomar foto"→ Cámara escribe en el archivo temporal→ importarArchivo() endereza y achica→ item.copy(fotos = fotos + nombre)→ Autoguardado → guardarItem()

D. Exportar un PDF

Ícono compartir en la parada→ Se guarda lo pendiente (guardar())→ DialogoExportarPdf→ PlanillaPdf.generarParada()→ Archivo en exportaciones/→ Ver / Compartir (Intent + FileProvider) / Guardar copia

E. Autoguardado al escribir

Tecla→ onValueChange → item = item.copy(…)→ Recomposición: el campo muestra el texto→ LaunchedEffect(item) espera 500 ms→ Sin cambios nuevos: onGuardar(item)→ Repositorio: memoria + JSON

12. Pruebas

Pruebas locales (en la PC)

app/src/test/java/com/example/appgeologia/RecorridoRepositoryTest.kt — 9 pruebas del repositorio y del modelo. Se ejecutan sin teléfono, en segundos:

  • Las paradas se numeran 1, 2, 3… y copian el proyecto del recorrido.
  • Los datos se mantienen al "reabrir la app" (se crea un repositorio nuevo sobre el mismo archivo).
  • Guardar una parada no borra sus items.
  • Los ids son únicos aunque el reloj devuelva siempre el mismo valor.
  • Un archivo dañado no rompe la app y se guarda una copia.
  • Se pueden leer datos de la versión anterior (con "horizontes").
  • tieneDatosSuelo() y fotosEnUso() funcionan como se espera.

Truco usado: el repositorio recibe por parámetro el scope de corrutinas y el reloj. En las pruebas se pasa Dispatchers.Unconfined (las escrituras pasan al instante) y un reloj fijo. Esto se llama inyección de dependencias y es lo que hace al código fácil de probar.

Pruebas instrumentadas (en el teléfono o emulador)

app/src/androidTest/…/PlanillaPdfTest.kt — genera fotos de prueba, arma el PDF de una parada y de un recorrido, verifica la cantidad de páginas y guarda cada página como PNG en /sdcard/Android/data/com.example.appgeologia/files/pdf-test/.

Cómo ejecutarlas

  • En Android Studio: clic derecho sobre la carpeta test o androidTest → Run Tests, o el triángulo verde junto a cada prueba.
  • Desde la terminal: gradlew testDebugUnitTest (locales) y gradlew connectedDebugAndroidTest (con un teléfono o emulador conectado).

13. Receta: agregar un campo nuevo a la planilla

Ejemplo: agregar "pH" a cada item. Es un buen ejercicio porque recorre todas las capas.

  1. Modelo — data/recorrido/Modelos.kt, dentro de ItemParada: 
    val ph: String = "",   // con valor por defecto: los JSON viejos se siguen leyendo
  2. Formulario — ui/recorridos/EditarItemScreen.kt, dentro de CamposSuelo, en la sección que corresponda: 
    CampoTexto("pH", h.ph, { cambiar(h.copy(ph = it)) }, teclado = KeyboardType.Decimal)
  3. PDF — pdf/PlanillaPdf.kt, agregar una fila a la lista filas donde quieras que aparezca: 
    Fila(null, "pH", { it.ph }, alto = altoFila),
  4. Listo. No hace falta tocar el repositorio ni el ViewModel: guardan el item completo. tieneDatosSuelo() también lo considera solo.
Si el campo tiene opciones fijas (como Humedad): definí un GrupoOpciones en OpcionesSuelo.kt, usá SelectorOpciones en el formulario y pasá el grupo como cuarto parámetro de Fila; el PDF dibujará las opciones con la elegida encerrada en un círculo.
Ojo con el alto de página: la tabla ya ocupa casi toda la hoja A4. Si agregás varias filas, puede que tengas que bajar altoFila (16 puntos) o mover las observaciones a otra página.

14. Ejercicios para practicar y glosario

Ejercicios (de más fácil a más difícil)

  1. Colores: cambiá la paleta en ui/theme/Color.kt y Theme.kt y mirá cómo cambia toda la app.
  2. Texto de bienvenida: modificá el encabezado de InicioScreen.kt y agregá un cuarto contador ("Items").
  3. Sugerencias: agregá opciones a sugerenciasTextura en OpcionesSuelo.kt.
  4. Campo nuevo: seguí la receta del capítulo 13.
  5. Nuevo tipo de salida: agregá GEOLOGIA_ESTRUCTURAL("Geología estructural") al enum TipoSalida. Aparece solo en el diálogo; pensá qué campos distintos necesitaría.
  6. Ordenar paradas: en DetalleRecorridoScreen.kt agregá un botón para ver las paradas de la más nueva a la más vieja.
  7. Prueba nueva: en RecorridoRepositoryTest.kt escribí una prueba que verifique que cambiarEstado() finaliza un recorrido.
  8. Desafío: mostrar en el mapa el recorrido entero aunque las paradas estén lejos (pista: BoundingBox y zoomToBoundingBox de osmdroid).
